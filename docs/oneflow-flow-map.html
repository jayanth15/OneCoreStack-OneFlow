01 High-Level Architecture

OneFlow is a single-tenant ERP, packaged as a desktop-installable PWA. It has two runtime processes that talk HTTP to each other, plus an optional HTTPS reverse-proxy sitting in front of the Next.js server so that mobile devices on a LAN can install it as a native-feeling app.

Three-Tier Stack

Client Browser / installed PWA shell, React 19, Tailwind v4, shadcn/ui primitives
Edge HTTPS proxy (https-proxy.js) — Linux :4443, Windows :443, terminates TLS with the local OneFlow CA
App Next.js 16 (port 3000) + FastAPI / Uvicorn (port 8000). The two services are connected by a Next.js rewrite() rule that proxies /api/* to the FastAPI origin.
Data SQLite at backend/app/db/oneflow.db, auto-migrated on every startup; daily backup at 17:30 to backups/YYYY/MM/DD/

Network Flow (one request)

Browser
  │  HTTPS (443 / 4443)
  ▼
https-proxy.js   (Node TLS terminator)
  │  HTTP
  ▼
Next.js :3000   (App Router, PWA SW)
  │  rewrite /api/*  →  BACKEND_URL/api/*
  ▼
FastAPI :8000   (Uvicorn)
  │  SQLModel → SQLAlchemy
  ▼
SQLite file      (backend/app/db/oneflow.db)

Single-tenant assumption

One deployment = one customer. There is no multi-tenancy. Per-tenant customisation is achieved by build-time environment variables (MODULE_PLANNING, MODULE_ROUTING, etc.) that toggle optional routers in app/main.py. The SQLite DB is mounted as a Docker volume; the seed script (backend/seed.py) provisions the default admin / admin123 super-admin.

Service map

Frontend (Node / Next.js)

  • Port :3000 (HTTP, internal)
  • PWA service worker generated by @ducanh2912/next-pwa
  • Reverse-proxies /api/* → backend
  • Reachable from devices via the HTTPS proxy

Backend (Python / FastAPI)

  • Port :8000 (HTTP, internal)
  • Uvicorn (ASGI) under app/main.py
  • 25 routers mounted under /api/v1/*
  • SQLite via SQLModel, with custom idempotent migrations

HTTPS Proxy (Node)

  • Port :4443 Linux / :443 Windows
  • Loads TLS cert from certs/oneflow-*.pem
  • Forwards plain HTTP to :3000
  • Forwards WebSocket upgrades (none used today, but supported)

04 Authentication Flow

OneFlow uses a two-token system: a short-lived access token in sessionStorage and a long-lived refresh token in an HttpOnly cookie. The frontend never sees the refresh token, so even an XSS can only steal the 30-minute access token.

1 — Login

POST /api/v1/auth/login
Body: { username, password }
        │
        ▼
[backend] verify_password (argon2) → User
[backend] create_access_token(user_id)   # 30 min
[backend] create_refresh_token(user_id)  # 30 days
[backend] hash_token(rt) → refresh_tokens row
[backend] Set-Cookie: oneflow_refresh=rt;
                          HttpOnly; SameSite=Strict;
                          path=/api/v1/auth
        │
        ▼
Response: { access_token: "eyJ…" }
        │
        ▼
[frontend] sessionStorage["oneflow_access_token"] = access_token
[frontend] GET /api/v1/auth/me → CurrentUser
[frontend] sessionStorage["oneflow_user"] = JSON.stringify(user)
[frontend] router.push("/dashboard")

2 — Silent refresh (on 401)

any API call → 401
        │
        ▼
apiFetch() catches 401
        │
        ▼
POST /api/v1/auth/refresh     (cookie auto-sent)
        │
        ▼
[backend] decode_token(rt) → user_id
[backend] find refresh_tokens row by hash
[backend] mark OLD row as revoked = true
[backend] create new refresh_token, store hash
[backend] Set-Cookie: oneflow_refresh=new_rt
        │
        ▼
Response: { access_token: "eyJ…" }
        │
        ▼
[frontend] sessionStorage["oneflow_access_token"] = new
[frontend] retry original request with new token
            (skipRefresh: true to prevent loop)

3 — Logout

POST /api/v1/auth/logout  (cookie auto-sent)
        │
        ▼
[backend] hash_token(cookie) → mark refresh_tokens row revoked=true
[backend] Set-Cookie: oneflow_refresh=; Max-Age=0
        │
        ▼
Response: 204 No Content
        │
        ▼
[frontend] sessionStorage.removeItem("oneflow_access_token")
[frontend] sessionStorage.removeItem("oneflow_user")
[frontend] router.push("/login")

Authorisation model

Roles (string in User.role)

super_admin ─► all permissions
   ▲
admin ─► most permissions
   ▲
manager ─► scoped by CSV flags
   ▲
worker ─► most-restrictive

Per-user boolean flags

  • can_create_receipt
  • grn_access
  • dispatch_access
  • gate_pass_access
  • purchase_access

Admin / super_admin always bypass these.

Per-user CSV columns

  • inventory_access — view types
  • inventory_edit — edit types
  • request_departments — dept IDs
  • request_inventory — requestable types

Empty CSV = "all allowed" for access/request; empty = "none allowed" for edit.

Password hashing: Argon2 (via argon2-cffi).
JWT signing: HS256 with the SECRET_KEY env var.
Default in dev: SECRET_KEY="dev-secret-key-do-not-use-in-production" — must be rotated before going live.

05 Request Lifecycle (step-by-step)

A complete trace of one authenticated CRUD operation, from the user clicking a button to the database round-trip and back.

── Example: a manager loads the spares list ── [browser] useEffect on /dashboard/inventory/spares └─► apiFetchJson("/api/v1/spares/categories?page=1&page_size=20") [lib/api.ts] const token = sessionStorage.getItem("oneflow_access_token") fetch("/api/v1/spares/categories?…", { credentials: "include", # cookie for refresh headers: { "Content-Type":"application/json", Authorization: "Bearer <access_token>" } }) [Next.js :3000] Rewrite rule: /api/:path* → ${BACKEND_URL}/api/:path* # http://localhost:8000 # no body inspection, no caching (PWA SW ignores /api/*) [FastAPI :8000] app.include_router(spares_router) @ /api/v1/spares ▼ @router.get("/categories") # spares.py Depends(get_current_user) ──► HTTPBearer() reads Authorization header ▼ decode_token(token) # HS256, type="access" ▼ session.get(User, user_id) # ensure is_active=True ▼ session.exec(select(SpareCategory)…).all() ▼ pydantic schemas serialise rows → JSON list [response] 200 OK [{ id, name, code, is_active, item_count, … }, …] [lib/api.ts] apiFetchJson parses JSON → Promise<SpareCategory[]> resolves useState<SpareCategory[]>(data) # re-render

The 401 path (token expired mid-session)

[fetch] returns 401 # access token expired [apiFetch] not skipRefresh? → silent refresh fetch("/api/v1/auth/refresh", { method:"POST", credentials:"include" }) [backend] hash cookie → find refresh_tokens row (revoked=False, not expired) rotate: revoke old, issue new, set-cookie return { access_token: "new…" } [apiFetch] setAccessToken(new) retry original request, skipRefresh=true # to break the loop [fallback] if refresh also 401 → clearAccessToken(), window.location="/login"

Frontend data-fetching pattern (universal)

// every page looks like this — no React Query, no SWR
"use client";
import { useEffect, useState } from "react";
import { apiFetchJson } from "@/lib/api";

const [data, setData]       = useState<T | null>(null);
const [loading, setLoading] = useState(true);
const [error, setError]     = useState<string | null>(null);

useEffect(() => {
  setLoading(true);
  apiFetchJson<T>("/api/v1/...")
    .then(setData)
    .catch((e: unknown) => setError(e instanceof Error ? e.message : "Failed"))
    .finally(() => setLoading(false));
}, [deps]);

// patterns observed across the codebase:
- Manual pagination: URLSearchParams("page","page_size")
- Debounced search: 300 ms setTimeout
- Auto-refresh: setInterval(load, 30_000)
- Optimistic updates: local state first, API second
- Multi-item forms: array of { _key, … } rows with add/remove buttons

10 Core Workflows

The four most important end-to-end flows, from a user action to its data effect.

① Login → Dashboard

Browser lands on /
app/page.tsx is a server component that redirect("/login")s.
User submits credentials
app/login/page.tsx calls apiLogin(username, password), which POSTs /api/v1/auth/login.
Backend issues tokens
Argon2 verifies password → creates 30-min access JWT + 30-day refresh JWT → stores SHA-256 of refresh in refresh_tokens → sets oneflow_refresh HttpOnly cookie (path /api/v1/auth, SameSite=Strict).
Frontend stores session
Access token → sessionStorage["oneflow_access_token"]. Then GET /api/v1/auth/me → full user object → sessionStorage["oneflow_user"].
Router push → /dashboard
dashboard/layout.tsx wraps content in <AuthGuard>; isAuthenticated() returns true; sidebar polls counts; TopBar polls notifications; page renders KPIs.

Self-fulfillment is blocked: the requester cannot POST /receipts for their own request. Multi-dept requests (items with explicit per-line department) relax this rule.

③ Production order → BOM deduction

Admin creates production order
POST /api/v1/production/orders with plan_id + qty_planned. Schedule status auto-advances to in_production.
Job cards created per process step
Each step in the plan's production_process gets a job_card. Multi-worker cards store worker_names as a JSON array.
Workers report output
PUT /api/v1/production/jobs/{id} updates qty_produced, status, etc. Workers see only their own cards; admins see all.
BOM auto-deducted + scrap auto-created
On qty_produced increase, the router looks up bom_item for the product → deducts raw materials from inventory_item → writes inventory_history rows. Any scrap in the BOM is added to a scrap-typed inventory item.
Status propagation upward
When all processes have produced, effective_qty = MIN(qty_produced) is computed; FG inventory is credited; order → completed → plan → completed → schedule → completed.

11 PWA, HTTPS & Install

OneFlow is designed to be installed as a standalone app on phones and tablets. Because mobile PWAs require HTTPS, a Node reverse-proxy in front of Next.js terminates TLS with a self-signed OneFlow CA. Devices install the CA once via /setup and Chrome then offers the install prompt automatically.

Lifecycle

1 · Generate certs (one-time)

install.bat (Windows) or start-linux.sh creates a local CA and a server cert. Linux uses PEM (certs/oneflow-*.pem); Windows builds a .pfx bundle (passphrase oneflow-local).

2 · Install HTTPS proxy

https-proxy.js listens on :4443 (Linux) or :443 (Windows). Linux also adds an iptables rule redirecting :443 → :4443 (since non-root can't bind 443).

3 · Device trusts CA

Phone visits http://<server-ip>:3000/setup → downloads oneflow-ca.crt → installs it. Then opens https://<server-ip> → Chrome offers "Install App".

12 Startup, Migrations & Backups

Everything happens in the FastAPI lifespan context manager in app/main.py. Idempotent — safe to run on every boot.

Startup sequence

1. init_db()
Imports app.models → calls SQLModel.metadata.create_all(engine). Chmods the DB file to 0o664 for cross-container UID compatibility.
2. run_migrations()
Safe, idempotent column adds: spare_item_variant.reorder_level, spare_item_history.variant_label, six new user flags, weeder_item.category_id, receipt/department/purchase_request/bom_item columns, and three indexes.
3. ~35 _migrate_*() functions
Each checks PRAGMA table_info / sqlite_master first. Some ADD COLUMN, some rebuild tables (SQLite can't DROP COLUMN), some rename (customers → vendors), some backfill default data (e.g. changed_by_username from changed_by_user_id).
4. _seed_customers_from_schedules()
Populates the new Vendor table with names that exist in Schedule.customer_name so old data still resolves to a vendor.
5. _auto_seed_if_empty()
If users is empty, creates the default admin / admin123 super-admin and links it to the Production department.
6. start_scheduler()
Arms a single threading.Timer for 17:30. When it fires: sqlite3.Connection.backup() streams 256-page chunks to backups/YYYY/MM/DD/oneflow.db, then runs cleanup_old_backups(retention_days=90) which deletes day folders older than 90 days and prunes empty month/year dirs. The timer is daemon-threaded and self-reschedules.

13 Notable Issues & Gotchas

Things worth knowing if you're about to extend or debug the system.

🐞 Bug — missing decorator in gate_passes.py:132
The function get_gate_pass(gp_id, …) is missing its @router.get("/{gp_id}") decorator, so GET /api/v1/gate-passes/{gp_id} is unreachable. The function body is intact; adding the decorator one line above fixes it.
🐞 Mild — duplicate departments_router.public_router include
app/main.py:1303-1304 includes the same router twice. Harmless (FastAPI dedupes route registrations by (path, method)) but noisy and worth removing.
⚠ Alembic listed but unused
requirements.txt pins alembic==1.18.4 but there is no alembic/ directory and no migration runner. Schema management is done by hand-rolled _migrate_*() functions. Adding Alembic would be a significant quality-of-life improvement.
⚠ Postgres driver bundled but not exercised
psycopg2-binary is in requirements.txt and the config supports DATABASE_URL=postgresql+psycopg2://…, but the in-place migration helpers are SQLite-only (use PRAGMA table_info). Switching to Postgres in prod would need a small refactor of app/core/database.py.
⚠ Dark-mode CSS exists but no toggle
app/globals.css defines full :root + .dark token sets and every component has dark: variants, but the .dark class is never applied anywhere. Adding a toggle is a 5-line change.
ℹ No tests anywhere
Neither the backend nor the frontend ships tests. The PLAN.md verification checklist includes only tsc --noEmit and a port check.
ℹ No WebSockets
The websockets package is in requirements (transitive), but no @app.websocket or @router.websocket endpoints exist. Live updates are done by client-side polling every 30 s.
